# Native three-phase QA workflow

Use `native_workflow.py` to replace instance-specific preparation, activation and report-publication scripts. It composes the public `native_graph`, `staged_qa` and `native_finish` modules; it does not create a scheduler, invoke heartbeat manually, or copy historical state.

## Prerequisites

Use an explicitly approved target organization with a project, an issue-bound CEO coordinator, admitted OMP actors for prepare/closeout, and a dedicated model-free `process` actor. Create the three phase issues as **unassigned fresh backlog issues in the same project**, with no existing adapter overrides. Creation and permission approval use the target installation's normal management interfaces; this helper does not silently create or approve agents/projects/issues.

Keep the repository, source and plan files operator-controlled. The plan is not task text. Credentials remain outside the plan and are supplied by the genuine native run.

## Trusted plan

Save a JSON object with:

- `schema`: `native-qa-workflow/v1`.
- `company_id`, `ceo_id`, `coordinator_issue_id`, `project_id`: exact target UUIDs.
- `issue_ids`: distinct `prepare`, `machine`, `closeout` UUIDs, also distinct from the coordinator.
- `actors`: each phase has `id` and `adapterType`; prepare/closeout use registered `omp_local` or `omp_native_json_local`, machine uses its dedicated `process` actor.
- `source_project`: absolute path to the supported Markdown-link-audit source project or bundled reference fixture.
- `work_root`: fresh absolute evidence root, disjoint from the source.
- `plan_path`: absolute path of this exact JSON file; the CLI checks this binding.
- Optional `allowed_http_origin`: an explicitly approved single remote plaintext origin. It does not select the API host; it supplies the origin opt-in to the generated phase commands.

The workflow inherits the component's reference-project contract; it is not a universal arbitrary-test runner. It fixes program entrypoints rather than accepting an executable or API host from plan fields.

## Generate, then activate deliberately

From the repository root:

```sh
# Pure payload generation: no API calls and no evidence-root creation.
python3 -B segmented-qa/native_workflow.py plan --plan /absolute/operator-plan.json

# Run only INSIDE the genuine, expected native CEO coordinator run:
python3 -B segmented-qa/native_workflow.py activate --plan /absolute/operator-plan.json --execute
```

Activation checks the running CEO and its uniquely bound coordinator issue, company/project, admitted actor types/states and all fresh phase issues. It configures closeout, then machine, then releases prepare. Each mutation has a durable exclusive intent and exact readback. Existing task overrides are rejected, not silently preserved or overwritten. Completion of the coordinator means dispatch was verified, **not** that QA passed (`businessAcceptance: unverified`).

The generated phase instructions call:

```sh
# Expected prepare actor's genuine native run only:
python3 -B segmented-qa/native_workflow.py prepare --plan /absolute/operator-plan.json --execute
# Expected closeout actor's genuine native run only:
python3 -B segmented-qa/native_workflow.py publish --plan /absolute/operator-plan.json --execute
```

The machine phase is a fixed process command generated by the existing graph builder. Paperclip remains responsible for dependency scheduling.

## Runtime and success boundaries

Runtime identity comes from `PAPERCLIP_API_KEY`, `PAPERCLIP_API_URL`, `PAPERCLIP_AGENT_ID`, `PAPERCLIP_COMPANY_ID`, `PAPERCLIP_RUN_ID` and optional `PAPERCLIP_TASK_ID`; no credential file is read. Every present native issue binding must agree; `taskKey` is not an issue identity. The expected issue is pinned again at the native finish boundary, even if the task ID was omitted. Conflicting task IDs are refused rather than overwritten.

HTTPS and loopback HTTP follow the existing publisher policy. Remote plaintext needs `SEGMENTED_QA_ALLOWED_HTTP_ORIGIN` to match exactly; activation must also receive this approved runtime opt-in. Redirects and proxy environment variables are not used.

- Prepare freezes/verifies the contract and finishes only its own bound issue; it never runs machine QA.
- Publish verifies the machine receipt and report bytes, writes the formal `segmented-qa` issue document once, and compares exact key/title/format/body before finishing closeout.
- Durable intents remain after success. Repeated calls or uncertain effects require reconciliation, not retry permission. Never delete an intent to force replay.
- Source hashes protect integrity within a trusted filesystem, not against an attacker controlling the plan or package.
- Client-side checks cannot eliminate server GET→PATCH races. A differing readback is not inferred success; preserve the intent and inspect the actual target.
- Automated-subset results retain manual product acceptance `PENDING`.

## Reproduce verification

```sh
npm run test:segmented-qa
```

The default suite includes workflow refusal/identity/override/publication tests and a real-module composition test against a **synthetic loopback control plane**. The latter executes the graph-generated commands, runs the bundled product's actual 23 black-box checks, verifies single execution and report readback before finish, and confirms repeat prepare/publish calls add no HTTP requests. This is committed regression coverage, not a live-server scheduler, OMP/provider, Telegram or deployment certification.

# 完整重建计划

状态：实施与分批发布中，尚未完成完整重建验收。初始基线：`81568198ed322ee93973c1ebe15c1373cd4c3f44`。

## 目标与边界

从本仓库的干净检出开始，使用明确版本的外部宿主与可安装依赖，仅补目标环境非秘密配置和外部提供的凭据，即可重建本集成已交付的能力。不能依赖作者机器上的私有脚本、缓存、相邻 checkout、未登记的 node_modules 修改或历史运行证据。

重建的是集成软件、接线方式及已交付能力，不是原组织的数据克隆。真实任务、聊天历史、agent UUID、凭据、cursor、锁、UNKNOWN 写意图和原有运行状态不进仓库、不跨环境复制。第三方宿主不必全部 vendoring，但来源、版本、兼容范围、构建与安装方法必须明确。

本计划不授权更换当前部署、重启服务、迁移组织、扩张权限或发起新的真实业务任务。生产升级与干净目标重建分开验收。打包不等于修复所有开放问题，未实现的通用超时恢复等能力不得写成重建后已具备。

## 已知资产与缺口

- 仓库已有事件桥、Telegram 注入插件、`omp_native_json_local` 适配器、分段 QA 组件、配置校验与部署脚本生成器，以及相应测试。
- CEO 管理 CLI、服务端权限适配尚未纳入公开仓库，需要审计、去实例化与测试依赖闭合。
- 实际部署使用的 `omp_local` 与仓库 `omp_native_json_local` 不是同一执行契约。先确认真实注册入口和行为差异，再决定提供兼容安装档还是经单独验收统一；不能悄悄更换执行引擎。
- 恢复读取、workspace 交付引用、wake 参数与原生截止门禁存在隔离候选；须与当前基线逐项核对，不能因为已有离线通过记录便直接当作线上产品发布。
- 实例绑定的 QA 激活脚本须区分通用产品逻辑与一次性运营动作。可复用逻辑改为参数化工具或模板；私人证据不能充当新检出的测试夹具。
- 现有 setup 仅覆盖其文档列出的接线步骤，不代表整个现役能力已经可重建。

## 最小交付路线

1. **冻结差异清单**：逐项记录仓库来源、现役来源、候选状态、许可证/来源、必要配置、宿主依赖及验收方法。区分已入库、可移植、需重构、刻意排除及未实现。
2. **闭合产品源码与配置**：纳入必要 CLI、版本绑定补丁及参数化模板；统一非秘密配置入口。补丁必须校验目标版本和文件指纹，默认仅检查/预览，未知基线拒绝应用，不自动放宽安全边界。
3. **闭合安装与注册**：明确宿主安装、适配器注册、插件安装、CEO 工作约束模板、分段 QA process 角色及任务级配置的生成与核验路径。凭据由操作者在外部安全供给，不生成长期 Board 凭据。
4. **干净目标演练**：在隔离工作区，以新检出、新 HOME/状态目录、合成配置与明确安装的宿主执行文档路径。不借用当前部署的依赖树、身份或数据。
5. **发布收口**：独立审查；核验精确提交的 CI；更新中英 README、部署/兼容性说明与 issue，再按授权发布。需要真实认证、付费模型、服务或权限变化的验收另列实际前置条件，不能用 mock 替代后宣称全部通过。

- [ ] 目标配置有严格校验，路径不依赖作者目录；配置中的身份、执行器、消息目标与持久状态归属一致。

- [ ] CEO CLI 能通过文档化入口加载，保留组织归属、真实运行上下文、精确写后读回、未知副作用不重放与人工对账边界。
- [ ] 所有必要宿主补丁均可从受支持的干净基线生成/应用/核验；不依赖手工编辑运行目录，版本漂移明确失败；回退不覆盖其他维护者的修改。

- [ ] 分段 QA 的准备、机器执行、只读收口、正式报告发布和原生任务状态登记可通过参数化入口重建；单次执行及依赖自动接续有目标环境证据。
- [ ] Telegram 消费/用户可见交付与内部注入、API accepted、run succeeded 分开验证。未取得真实平台证据的项目明确未验收。

- [ ] README 命令与实际演练一致；报告区分离线、宿主组合、真实系统与未覆盖项，不把旧部署成功当作新检出成功。

## 审计收敛与实施顺序

已完成两项只读源码分析，并由协调者检查服务端补丁报告、现役适配器 manifest 与仓库 setup 源码。结论限源码与交付闭包，不代表重新认证了线上加载字节。

1. **CEO CLI**：先移植已部署版本的安全能力，保留独立配置兼容入口，再通过仓库共享配置适配接线。后续 recovery/workspace 候选单独登记、验证，不因可重建目标便默认为现役版本。
2. **服务端补丁**：完整范围为 `routes/agents.js`、`services/recovery/service.js`、`services/acknowledged-native-stop.js`。必须核验公开 server 包能否还原固定基线，以及 authz/authorization/heartbeat 的只读依赖；不能重新运行生成器来接受未知基线。保留同公司、有效 CEO、target-scoped configure grant、pending hire 拒绝、真实审计和 native stop receipt 要求，不新增 role-only fallback。
3. **OMP 两种契约**：保留 `omp_local` 与 `omp_native_json_local` 的明确区别。前者包含 `index.mjs`、`skills.mjs`、`runtime-skills.mjs`、`output-parser.mjs`、`omp-baseline.mjs`；当前基线 manifest 未将 deadline-window/deadline-jobs 测试纳入默认入口，移植必须核对实际套件。不得通过薄适配器静默替代现役能力，也不声称 deadline 环境变量等于确定性收尾预算。
4. **原生 QA 完整入口**：参数化准备并完成、正式文档发布、逆依赖顺序激活与协调完成。原生状态完成 helper 不能替代正式文档上传；保留精确身份、独占写意图和未知效果不重试。
5. **统一装配和演练**：现有 setup 只生成插件接线与桥 argv，不负责完整角色/适配器/服务装配。先补预览与受控执行入口，再在干净隔离目标验证，不将生产任务状态带入重建。

优先固定受支持的当前宿主基线，不在重建过程中顺便升级。若公开包无法还原补丁基线，将此作为明确阻塞，补查前置差异后再决定适配，不静默放宽 hash 门禁。
